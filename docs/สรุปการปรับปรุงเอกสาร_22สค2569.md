# สรุปการปรับปรุงเอกสาร RBWF (รอบ 22 สิงหาคม พ.ศ. 2569)

เอกสารนี้สรุปจุดที่ปรับในช่วงบ่ายวันนี้ เพื่อใช้พูดประกอบวิดีโอให้ผู้ประเมินตรวจสอบอีกครั้ง  
คลัง: [ISO-IEC-29110-RBWF](https://github.com/symphosoftworkflow/ISO-IEC-29110-RBWF) สาขา `main`

---

## จุดที่ 1 — แจ้งการส่งมอบซอฟต์แวร์เสร็จสมบูรณ์ใน VLD วันที่ 29 พ.ค.

**ทำไมต้องแก้:** VLD งวดที่ 3 และ Final Delivery ลงวันที่ 29 พฤษภาคม พ.ศ. 2569 แต่ยังไม่ระบุชัดว่าส่งมอบระบบซอฟต์แวร์ที่เสร็จสมบูรณ์ให้ลูกค้าแล้ว

**แก้ที่ไหน**

- `BASELINE/RBWF_VLD/RBWF_VLD_20260529.md` (งวดที่ 3)
- `BASELINE/RBWF_VLD/RBWF_VLD_FINAL_20260529.md` (Final Delivery)

**สาระสำคัญ**

- ระบุส่งมอบระบบ Rabbit Workflow ที่เสร็จสมบูรณ์ (API Backend + Frontend) แก่ **บริษัท ซิมโฟร์ซอฟท์ จำกัด**
- งวดที่ 3 เพิ่มรายการยืนยันลำดับ 7 และหมายเหตุ `workflowv2.rabbittile.com`
- Final คงผล VALIDATED และวันเดียวกับงวดที่ 3

**Commit:** `8c14c9a`

## จุดที่ 2 — ชี้แจงซอฟต์แวร์ที่ส่งมอบในงวดที่ 2 (ยังไม่ใช่ระบบหลัง UAT)

**ทำไมต้องแก้:** SOW/PMP ระบุงวดที่ 2 มีซอฟต์แวร์ แต่ยังไม่เสร็จและยังไม่ UAT — ผู้ประเมินถามว่าส่งส่วนไหนบ้าง

**แก้ที่ไหน**

- `BASELINE/RBWF_VLD/RBWF_VLD_20260327.md`
- `BASELINE/RBWF_VLD/RBWF_CLARIFY_INSTALLMENT2.md` (talking points)

**สาระสำคัญ**

- งวดที่ 2 = **ซอฟต์แวร์หลักบน Staging** (~75% ตาม PSR) + SDD ไม่ใช่ระบบพร้อมใช้งานสมบูรณ์
- ระบุโมดูลที่สาธิต: สต็อก / ขาย / ช่าง / การเงิน และการเชื่อมโยงข้อมูลบนสแตกเดียว
- ลูกค้ารับทราบว่าพัฒนาต่อถึง 15 เม.ย.; UAT อยู่พ.ค. (งวดที่ 3 / Final)

**Commit:** `1526c48`

## จุดที่ 3 — ย้าย CRR 004 ให้ตรงช่วง System Testing (TC-STK-02)

**ทำไมต้องแก้:** CRR 004 (โฟกัส Barcode) ลงวันที่ 10 มี.ค. ซึ่งอยู่ก่อนช่วงทดสอบระบบ — เป็นไปไม่ได้ถ้าพบตอนทำ Test Case

**แก้ที่ไหน**

- `BASELINE/RBWF_CRR.md` (รายงาน 16/04/2026, คาดเสร็จ 26/04/2026, พบระหว่าง TC-STK-02)
- sync MOM/PSR มี.ค. (เอา ISS-005 ออก) และเม.ย. (ใส่ ISS-005)
- `BASELINE/RBWF_TR_v1_0.md` หมายเหตุ TC-STK-02

**สาระสำคัญ**

- Defect หน้าสแกน Barcode พบในรอบ System Testing 16–17 เม.ย. ตาม SWC/PMP
- เลขทะเบียน CRR 004 และคู่ ISS-005 คงเดิม แค่ย้ายวันที่/บริบท

**Commit:** `b20608f`

## จุดที่ 6 — ขยาย TP/TR เป็นแถวรายเงื่อนไข (สถานะแยกได้)

**ทำไมต้องแก้:** ผู้ตรวจเห็นว่า Test Conditions / ความคาดหวังสั้นหยาบ และ Tester ต้องบันทึกผลแยกต่อ sub-case

**แก้ที่ไหน**

- `BASELINE/RBWF_TP_v1_0.md` (เวอร์ชัน 1.1)
- `BASELINE/RBWF_TR_v1_0.md` (เวอร์ชัน 1.1)

**สาระสำคัญ**

- หนึ่ง Test Condition + ความคาดหวัง = **หนึ่งแถว** มีคอลัมน์สถานะ/หมายเหตุ
- **คง Test Case ID เดิม** แสดงเฉพาะแถวแรกของแต่ละเคส (ไม่แตกรหัสย่อย เพราะลิงก์ RTM/SWC/UAT)
- TR มีผล `pass` ครบทุกเงื่อนไข (~75 แถว) สอดคล้อง TP
- TC-STK-02 เงื่อนไขรับเข้า: ระบุ **scan เอกสารจาก barcode** ให้สอดคล้อง CRR 004

**Commit:** `576bbbb`

## ลำดับแนะนำสำหรับวิดีโอ (ประมาณ 5–8 นาที)

1. **เปิดคลิป:** สรุปว่าวันนี้ปรับหลักฐานตามข้อสังเกตผู้ประเมิน 6 จุด บนคลัง GitHub  
2. **จุด 1:** เปิด VLD 29 พ.ค. / Final — ชี้ประโยคส่งมอบซอฟต์แวร์ครบให้ซิมโฟร์ซอฟท์  
3. **จุด 2:** เปิด VLD 27 มี.ค. + ไฟล์ Clarify — อธิบายงวด 2 = Staging หลัก ไม่ใช่หลัง UAT  
4. **จุด 3–4:** เปิด CRR — ชี้วันที่ 004 ในเม.ย. + ข้อความ 003/006  
5. **จุด 5:** เปิด SCM §12 — ชี้ LA-OR และพาธ BACKUP/RBWF_REPOSITORY_BACKUP  
6. **จุด 6:** เปิด TP แล้ว TR — แสดงแถวย่อย + สถานะ pass + เงื่อนไข barcode  
7. **ปิดคลิป:** ยืนยันไม่เปลี่ยนรหัส TC / มูลค่างวด / ลายเซ็นหลักนอกเหนือที่ระบุ และพร้อมให้ผู้ประเมินตรวจซ้ำบน `main`
